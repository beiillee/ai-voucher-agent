**入口**：`app.py`（Streamlit）、`main.py`（CLI / PyInstaller 打包）、`run_tests.py`（测试）

**数据流**：

```
PDF ──pdf_parser──> pages[{page_no, text, source, ocr_confidence}]
                        │
                  voucher_extractor（按凭证号众数分组）
                        │
                    pdf_vouchers
                        │
Excel ─excel_analyzer──> ledger_vouchers ──reconciliation──> pairs[{match_status, diff}]
                                                              │
                                            anomaly_detector ─┴─> anomalies（10 类）
                                                              │
                                       ledger_risk_analyzer ──┴─> risk_clues（6 类）
                                                              │
                                                     report_generator ──> xlsx（5 Sheet）
```

**技术栈实况**：pdfplumber、PyMuPDF、pytesseract、Pillow、pandas、openpyxl、streamlit、python-dotenv、openai（可选）。**无 SQL、无 sklearn、无 matplotlib/plotly**。

### B 类 · 已实现但存在问题

按严重度排序。

#### B1（阻断）演示数据与凭证 PDF 不配套

`data/demo_ledger.xlsx` 有 535 张凭证，但没有 1211 号，也没有 999 号。用它跑账证核对，匹配率恒为 0，报告里「核对结果」只有 2 行且全是 PDF_ONLY。

- 影响：任何演示、截图、README 取数都会失真；面试演示会当场穿帮。
- 引入原因：前序会话生成演示账时只服务于风险分析，没考虑账证核对需要凭证 PDF 侧配套。
- 处置：需重新生成一份演示凭证 PDF（复用 `make_sample_data.py` 的 PDF 生成逻辑），其凭证号从 `demo_ledger.xlsx` 中抽取，并与账内金额、日期、科目一致。

#### B2（阻断）测试未随报告结构同步

`tests/test_integration.py:47` 断言 3 个 Sheet，实际 5 个。`tests/test_report_generator.py:62` `test_three_sheets` 同理需确认。

- 影响：`run_tests.py` 返回非零，CI 若接入会红。
- 处置：把断言改为 5 个 Sheet，并新增对「风险线索」「风险概览」内容的断言。

#### B3 仅支持单份 PDF，与「批量上传」目标冲突

`app.py:43` 与 `main.py:30` 都只接受一个 PDF 路径：

```python
pdf_file = st.file_uploader("① 会计凭证 PDF", type=["pdf"])
```

- 影响：任务书第二阶段第 1 条要求「一次上传多份 PDF」，当前不满足。
- 连带风险：即使改了上传控件，`voucher_extractor.extract_vouchers` 的跨页分组是按**全局凭证号众数**做的（`tools/voucher_extractor.py:200-210`）。多份 PDF 若凭证号重复（不同月份都有 1 号凭证），会被错误合并成一张。必须先把分组键改为 `(文件名, 凭证号)`。

#### B4 匹配未使用科目与摘要

`tools/reconciliation.py` 全文只在 `summary` 字典里出现过 `summary` 这个词，匹配逻辑仅依赖 `(type, period, seq)` 与借方金额。

- 影响：任务书要求匹配字段含「会计科目、摘要」，当前为零。凭证号缺失时（任务书第三层要求）只能靠金额+凭证号模糊，无法用科目和摘要缩小候选。
- 根因：PDF 侧根本没抽会计科目。`tools/voucher_extractor.py` 的 `_extract_page_fields` 返回字段里没有 account 类字段，只有 `counterparties` / `invoices` / `contracts`。

#### B5 匹配状态缺「疑似匹配」与「多条候选」，且一对多会静默丢数据

两个具体缺陷：

**其一，状态语义不足。** 当前状态枚举只有 5 个：`MATCHED` / `AMOUNT_MISMATCH` / `DATE_MISMATCH` / `PDF_ONLY` / `OCR_UNCERTAIN`。任务书要求区分 5 类：匹配成功、疑似匹配、无法匹配、多条候选、OCR 不完整。P1b（期间+编号，置信度 0.9）、P2（仅编号，0.7）、P4（模糊，0.6）命中后，只要金额对得上就一律标 `MATCHED`，读者无法从状态本身看出这是低置信匹配。

**其二，索引覆盖写。** `tools/reconciliation.py:24`：

```python
idx["by_key"][key] = lv      # dict 直接覆盖
```

同一 `(type, period, seq)` 若存在两条序时账凭证（重复凭证在真实账里很常见），后一条静默覆盖前一条，前者永远不会被匹配，也不会出现在任何异常里。`by_seq` 用了 `defaultdict(list)` 是对的，`by_key` 没有。

#### B6 无法定位到 Excel 原始行号

`tools/excel_analyzer.py` 构造 `records` 时只填 `STANDARD_FIELDS` 里的 15 个键，没有保存 pandas 读到的物理行位置。`line_no` 是账内自带的「行号/序号」列，样例账里为空，且语义不等于 Excel 第几行。

- 影响：任务书要求「序时账 Excel 行号」可追溯，当前做不到。审计人员拿到报告无法回到原表定位。

#### B7 异常清单缺文件名与 Excel 行号

`tools/anomaly_detector.py` 每条异常只有 7 个字段：`type` / `voucher_no` / `page` / `detail` / `debit_diff` / `credit_diff` / `is_info`。

- 缺：原始文件名（多文件场景必需）、Excel 行号、触发规则名（现在规则名塞在 `type` 里，没有独立的规则说明列）。
- 影响：任务书第四阶段第 4 条列了 8 项必需输出，当前缺 3 项。

#### B8 字段命名与统一 schema 不一致

任务书给的统一字段是 `ledger_date` / `voucher_no` / `summary` / `account_subject` / `debit` / `credit` / `amount` / `department` / `counterparty`；PDF 侧是 `voucher_date` / `voucher_no` / `summary` / `account_subject` / `debit` / `credit` / `total_amount` / `counterparty`。

实况：

| 任务书字段 | 项目现用名 | 状态 |
|---|---|---|
| `ledger_date` | `doc_date`（前序会话新增） | 名称不同 |
| `voucher_date` | `date` | 名称不同 |
| `account_subject` | `account` | 名称不同 |
| `total_amount` | `debit_total` | 名称不同 |
| `department` | 不存在 | **缺字段** |
| `summary` | `summary` | 一致 |
| `counterparty` | `counterparty` | 一致 |

- 影响：不阻断运行，但对接任务书规格、写文档、对外说明时会有理解成本。改名需同步改 10 处引用，建议放在 P1 一起做，不做二次改名。

#### B9 时间分析能力实际未验证

`doc_date` 是前序会话新增的字段，但两份样例账（`sample_ledger.xlsx`、`demo_ledger.xlsx`）的列结构里，`demo_ledger` 有「记账日期」，`sample_ledger` 只有「记账期间」。

- 影响：无日期列时，期末集中、周末入账、月度趋势全部走降级分支（只输出一条「未执行」说明）。降级逻辑本身是对的，但意味着**这套能力只在演示数据上验证过，没有在接近真实的账上验证**。

#### B10 重复交易只有精确匹配，没有相似度分级

`tools/ledger_risk_analyzer.py:373-395`：key 是 `(round(amount,2), 规范化摘要, 规范化对手方)`，三元组精确相等才归组。

- 缺：任务书要求的「高度相似」「疑似重复」两级。摘要差一个字（"报销差旅费" vs "报销差旅费用"）就检不出。
- 当前输出只有「高（同期）/ 低（跨期）」两档，是按期间分的，不是按相似度分的。

## 六、需要确认的 5 件事

1. **目录是否整体迁移到 `src/` 分层？** 任务书给了分层示例，但也写了「不要为了符合目录示例而破坏已有代码」。我倾向**不迁**，只在 `tools/` 内补职责注释和必要子包，理由是当前 8 个文件规模不足以支撑 6 层目录，迁移会带来 30+ 处 import 改动且无可测收益。若你希望目录结构与任务书一致（比如为了简历上写「按分层架构组织」），我可以在 P1 一次性迁完。

2. **字段名是否按任务书全量改名？** 改 `account → account_subject`、`date → voucher_date`、`doc_date → ledger_date`、`debit_total → total_amount`，影响 10 处引用 + 报告表头 + 前端展示。改名后与任务书完全对齐，但会动到已有测试断言。

3. **`department` 从哪来？** 现有两份样例账都没有部门列。要么生成演示数据时造一列，要么接受「有则分析、无则跳过」。真实序时账通常有部门辅助核算，建议做成可选字段 + 页面提示。

4. **SQL 怎么落？** 任务书总体目标提到 SQL，但当前架构是纯 pandas 内存计算。可选：① 用 sqlite 把 records 落地，分析用 SQL 查（能写进简历「SQL 分析」）；② 仅在 README 说明「数据量增大后可切 SQL」，不实做。我倾向 ①，因为它能让重复交易和结构分析用窗口函数写得比 pandas 干净，且是可演示的真功能。

5. **P0 收尾是否现在做？** 包括修 1 个失败测试、生成配套演示凭证 PDF、把前序改动提交一次。这三件事都不改变功能设计，但会让后续每个阶段都有干净的基线。你确认后我立即做，做完再停，等 P1 指令。

## 七、总体判断

**可用部分**：OCR 链路、凭证字段抽取、序时账列映射、四级匹配、10 类异常、6 类风险线索、5 Sheet 报告。这七块是项目真正的骨架，质量高于一般课程作业——尤其 OCR 双 psm 融合、借贷平衡修正、比较组排除结算科目、线索强制带基线这四处，是有判断力的设计。

### 8.3 收尾过程中修掉的两个缺陷

**其一，凭证日期跨凭证串组（`tools/voucher_extractor.py`）。**
`main_date` / `main_company` 原先取**全文件所有页**的众数，再赋给每一张凭证。单凭证样例看不出问题，一旦 PDF 含多张凭证，全部凭证的日期会变成同一天，`period` 随之错误，匹配从 P1 降级为 P2，并产生一批假的 `DATE_MISMATCH`。首次用新演示数据跑时就复现了：7 张凭证的日期全部成了 `2025-01-15`。
改为按「本凭证所辖页」取众数，全局众数仅在组内全部抽不到时兜底。

**其二，报告「结构分析口径」恒为空（`tools/report_generator.py`）。**
报告读 `coverage["structure_scope"]`，而分析器在「期间样本不足、未执行」分支写的是 `coverage["structure_mode"]`，键名不一致导致该行永远空白——恰好是读者最需要知道「为什么没做结构分析」的那一行。
改为两键兼容。现在小账簿会显示「未执行：满足样本量（≥20 条/期）的期间不足 2 个」，可见降级原因。
